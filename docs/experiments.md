# Experiments: what worked, what didn't, what's next

This file is the simulator's memory across improvement runs. Before choosing
what to work on, read **Next** and search **Didn't work** and **Considered**
for the idea, its file and its source. Don't retry something listed there
unless you say what is different this time. At the end of every run, kept or
not, update all four sections in the same commit as the change; if nothing
ships, commit this file alone.

`docs/improvement-log.md` has the full story of each shipped change; this
file is the short index, including everything that was tried and dropped.
Times are from the run's own machine (a 4-vCPU Xeon VM unless stated) and
only comparable within that run. "d" is the rotated surface code distance;
noisy runs use p = 0.001 and 10,000 shots unless stated.

## Next

In priority order. Replace this list at the end of each run.

1. **Fewer row gathers on the noiseless frames** (callgrind, x86-64-v3, 20,000 shots, one thread, 2026-11-22: `Tableau::row_into` 1.17e9 inclusive of 6.03e9 instructions, about 728k calls: 475k classifications plus 238k pull-backs; `next_measurement` 0.81e9 inclusive). The gather is now ~8 instructions per column bit; fewer calls would pay more: e.g. reuse the classification's row in `measure_shots` (it pulls the same `Z_q` back again in `gather_dormant`), or an AVX2 gather of four columns per load with a variable shift.
2. **`Group::anticommutes_into`** (0.47e9 inclusive at 20,000 shots; `extract` is 0.82e9 inclusive, mostly zeroing and allocating its three tables): XORs whole frame columns for every set bit of the pulled-back Pauli, while most frame columns are zero until the 50/50 measurements; skip zero columns as `extract` does (keep a bitmap of non-zero columns per group).
3. **One pass fewer per dense measurement, or several at once** (both paths): accumulate the next measurement's expectation inside the retirement, or sample several dense measurements at once as SymFT's "direct multi-coordinate sampling instructions" (arXiv:2607.28600) do, once a group is small. Profile first.
4. **More splits removed by exact identities** (noisy path): 0.1.12 removed the split at a rotation that grows the dense part. The same works at any rotation where some Pauli `Q` on the dense positions anticommutes with `P` and stabilizes the group's state. Count the remaining rotation splits on the benchmark circuits first.
5. **AVX-512 dense kernels behind runtime detection** (`is_x86_feature_detected!`), since wheels are built for x86-64-v3; and NEON kernels for the ARM wheels.
6. **Rerun `compare_nearclifford.py`** (noiseless near-Clifford against Aer): `nearclifford.csv` and the README table are from 0.1.0 (0.85 s at 1000 shots on 8 threads for the 100-qubit case; the example now takes about 0.24 s in all on 4 threads here). Needs about 1.5 hours of Aer timeouts on the VM.
7. **Stim's format on the near-Clifford backend.** Read `T`, `T_DAG` and Clifft's rotation gates and return detection events, so magic-state cultivation circuits run directly (and can be timed against Clifft, SymFT, SOFT (arXiv:2512.23037) and the cultivation sampler of arXiv:2509.08658).
8. **Stim reader and writer gaps.** `MXX`/`MYY`/`MZZ`, `SPP` and heralded errors in the reader; `to_stim` writing detectors and observables.
9. **Detection events without keeping every measurement record.** At d = 101 the 1.3 GB record is as large as the output.
10. **Qiskit layer**: Aer noise models (at least Pauli errors on Clifford circuits); classical control flow (`if_test`) on the backends that already measure mid-circuit; Cirq and PennyLane devices.
11. **Pauli propagation.** A compact string store, then weight truncation and noise (Angrisani et al., arXiv:2501.13101).
12. **A backend selector calibrated on the running machine.**
13. **Skip straight from one error to the next across blocks of frame words** (stabilizer noise). At d = 101 the countdown walks 1.1e9 steps for 7.2e7 errors (2026-10-28).
14. **Debug-build overflow in `NearClifford::on_positions`** (found 2026-11-14): with more than 64 active qubits in a symbolic compile the shift overflows; release builds wrap and the suite (run with `--release`) passes. Harmless in release (2026-11-20); fix for debug builds by skipping positions ≥ 64 in symbolic mode.
15. **Memory-neutral reuse of the top-level dense buffers** (see Didn't work, 2026-11-20): only an approach that does not raise peak RSS, e.g. writing the outcome-0 side of a retirement into the parent's own buffer (safe in place for Z-type Paulis; X-type needs a compaction pass).

## Didn't work

Don't retry these as they were tried. Each line says why. "Retry if" says
what new fact would justify another attempt.

**Noiseless near-Clifford: gathers and allocations (2026-11-22)**
- **The first `row_into`** (word accumulators, but indexing the full column table): `row_into` alone 1.05e9 + 0.15e9 (`cmp.rs`) instructions, about 13 per column bit, total 6.53e9. Slicing the table to exactly the last column read first dropped the per-load bounds check: 6.39e9. Kept the sliced form.
- **Dead end: "malloc is mostly `Tableau::row`'s `Vec`s"** (old Next item 1's guess): after the row and classifier buffers went, `RawVec::grow_one` of `Vec<Clifford>` (406,800 calls from `retire_plan`, plus the frame's log) and `pull_back`'s two result `Vec`s were the rest; `retire_plan`'s single allocation took the total from 6.39e9 to 6.03e9 together with `set_positions`.
- **Empty extract masks** (found by the new unit test): `extract` with no chosen shot panics in `chunks_exact_mut(0)`, as the old code did; a split never moves zero shots, so the test chooses at least one.

**Noiseless near-Clifford: buffer reuse and classification (2026-11-20, nothing shipped)**
- **A spare buffer per state, shrunk to the next output size** (`mod.rs` `retire`/`split_dense`, the replaced dense part kept for the next retirement): minor faults at 1000 shots, one thread, rose from 148k to 211k and sampling 0.509 → 0.571 s (10,000 shots 0.700 → 0.854 s). glibc raises its dynamic mmap threshold only on `free` of a mapped block; a shrinking `realloc` (`mremap`) does not, so later allocations stayed fresh mappings. Retry if the allocator is not glibc's.
- **The same spare without shrinking**: faults 148k → 129k, times within noise (e.g. 10,000 shots one thread 0.719 → 0.690 s, 100,000 2.506 → 2.529 s), peak RSS 261 → 324 MB on one thread and 260 → 503 MB on four.
- **A buffer pool shared by one run's tree** (`Arc<Mutex<..>>` in every state, best fit, buffers < 128 KB left to malloc, cap twice and then once the largest buffer): faults 148k → 82k; 10 interleaved rounds against 0.1.14, medians 0.868 / 0.943 (1000 shots, 1 / 4 threads), 0.942 / 0.921 (10,000), 0.988 / 0.991 (100,000); peak RSS 324 MB on one thread and 444-464 MB on four (from 260). Fit within 2× and evict the largest over the cap: RSS 324 / 377-390 MB but 0.953-1.102; cap at half the largest: 0.975-1.059. The gain came only from giving large buffers to small states. The faults are at levels with buffers ≥ 32 MB (mapped whatever the threshold), each level writes as much as the root, and reuse needs those pages resident, so it costs peak memory and lowers the largest state that fits. Retry if a memory-neutral way appears (Next item 15) or a user asks to trade memory for speed.
- **Classifying every pending measurement in one pass over the frame** (`Tableau::z_rows_touching`: OR of the dormant columns' x words and the active columns' x|z words, over the words of the Z rows, then a word shift; `next_measurement` picking from the bits). Same picks as one pull-back per qubit (unit test, both layouts, 70-130 qubits), but the pass reads 2 × 3 words × 100 columns, three rows' worth, while the scan reads 2.5 rows a call on average (counters at 20,000 shots: 191,727 calls, 475,048 classifications: 298,781 50/50, 176,267 dense, no fixed). `next_measurement` 1.34e9 → 1.80e9 / 1.45e9 / 1.64e9 instructions (zip iterators; branch-free with stack accumulators; indexed loops), 100,000 shots 1.06× slower. Retry if the scan's rows per call grow (more pending 50/50 measurements before the dense ones, or n > 64 × rows per call).
- **Dead end: the dense part empties before the last measurements** (assumed while choosing): counters showed `next_measurement` never runs with no active qubit on the 100-qubit example, at 1 shot or 20,000; 50/50 measurements with an X on a dormant qubit come before the last dense ones.

**Data layout and inlining (applies to every new channel or step type)**
- **Inline noise payloads** (2026-10-28, 2026-10-29, 2026-11-04). Each time they grew the hot structs and slowed noiseless circuits:
  - `Instruction::Noise` inline: 56 → 64 bytes, near-Clifford 14–15% slower.
  - `Step::Noise` inline: doubled each step, 21% slower at d = 51 at first, 5–8% after tuning.
  - Inline 15 `Pauli2` probabilities: `Instruction` grew to 150 bytes, noiseless d = 51 4–6% slower.

  Box the payload or keep a side-table index. A test pins `Noise` at 32 bytes and `Instruction` at 64.
- **Letting cold noise code inline into hot loops** (2026-11-04, 2026-11-06).
  - `PendingNoise::add` inlined into the reference shot made it about 5% slower.
  - The near-Clifford noise code made the noiseless 100-qubit example 5–9% slower, with identical callgrind instruction counts: fat LTO with one codegen unit placed the code differently.

  Mark noise paths `#[cold]` + `#[inline(never)]`.
- **Dead ends chasing the 2026-11-06 noiseless regression** (the cause was code placement, above):
  - compacting groups once a quarter of their slots are dead (+1.3% median, noise);
  - `rayon::join` for measurement splits (still 3–7% slower);
  - transparent huge pages (THP is madvise-only here);
  - swapping back the old terminal sampler (equally slow).

**Noiseless near-Clifford frames (`nearclifford/mod.rs`, 2026-11-18)**
- **Dead end: Next item 2's guess.** It named the per-bit `Vec`s of `Group` (as on the noisy path in 0.1.13). Timers (10,000 shots, one thread, 1.45 s of sampling) put the split's allocations at 0.16 s; classifying every pending measurement before each one was 0.44 s (98,423 dense measurements in 9,989 single-shot groups, up to 100 pull-backs each), and the collapses at splits 0.41 s. Flattening the records still paid once the classification was fixed (`extract` was then the largest item at 100k shots).
- **One generic kernel for both paths** (`retired_x` as a wrapper of `retired_x_into::<1>`) and the `Classifier` inside `NearClifford::kind` (used by the noisy compile): no slowdown was established, but noisy comparisons read medians up to 1.09-1.14 on some cases in some runs, on a VM whose A/A run read 0.77-1.43. Both reverted so that the noisy path's kernel and compile keep their source; the 40-round recheck then read 0.971-1.017. Retry if the noisy path wants the two-outcome kernel (it never retires both outcomes of one measurement today).
- **Retiring both outcomes into the parent's buffer in place** (considered while writing `retired_both`, not built): for a Z-type Pauli a forward gather is safe in place, but for an X-type one the partner `a0 ^ x` of a later output can be an index already written. Would remove the page faults of one child (Next item 1) at the cost of a compaction pass.
- **Skipping the compaction of the staying side of a split** (considered): the draws of a dense measurement are 64 per live word, at the shot's bit position, so a layout change changes the counts for a seed. Kept to keep 0.1.5-0.1.13's counts.

**Near-Clifford noise (`nearclifford/noisy.rs`)**
- **Dead end (2026-11-16): guessing where the error-independent time went.** The 2026-11-14 entry and Next guessed the final measurements' halving tree and its second expectation pass (kernel work). Timers showed kernels were 20 of 145 ms; the bookkeeping of splits (one `Vec` per classical bit, allocated twice per split) was 95. Time before guessing.
- **Column-major records gathered with BMI2 `pext`** (2026-11-16, considered while choosing the fix, not built): one `pext` per word instead of a bit per shot, but `pext` is microcoded (~250 cycles) on AMD Zen 1/2, which run the x86-64-v3 wheels, and it needs a portable fallback; shot-major rows make a split a row copy with no gather at all. Retry if records must stay column-major (e.g. for word-wide outcome writes on huge groups).
- **Dead end: running the new tests in a debug build** (2026-11-14). `cargo test --lib noisy` without `--release` panicked in `on_positions` (shift overflow at > 64 active qubits in the symbolic compile of the 70-qubit case), code this change does not touch. Run the suite with `--release`, as the README says; the bug is in Next.
- **The no-split change's counts digest check** (2026-11-14): not applicable, since fewer splits change the order of random draws. Correctness came from exact-distribution tests (a new one, plus a mutation check: removing the row flip fails four tests) and the chi-square agreement with Clifft.
- **Carrying the virtual images of the insertions forwards to find the rows** (2026-11-12, first version of 0.1.11's `link`): one slot per insertion (11,000 at 100 qubits, 29,000 at 200) conjugated by every virtual Clifford (5,700 / 22,000). Same rows, but 18–30 ms at 200 qubits, and `compile` still pulled back two dense images per noisy qubit: one shot took 1.04–1.56× 0.1.10's time (`compare_noisy_builds.py --shots 1`), about level at 100 shots. Neither skipping the words of slots not yet put in nor a 64×64 block transpose helped (1 shot at 200 qubits 81 → 78.5 ms), nor did chunks in parallel (1.31× on 4 threads), nor carrying the *virtual* checks backwards (still 30 ms: the virtual images are dense). Replaced by carrying the *physical* checks backwards through the physical gates, where errors are one-qubit Paulis: one shot 0.64–0.78 of 0.1.10's time.
- **All groups in lockstep, one operation at a time** (0.1.8, replaced 2026-11-08). Once errors split most shots off, every operation streamed all groups' dense parts through memory (439 groups × 2^14 amplitudes, 112 MB per 640-shot batch): 4–10 ns per amplitude. Run groups depth first through a compiled program instead.
- **Branch-free dense kernels alone** (2026-11-08): visiting only written indices, coefficient as phase × parity sign. On the lockstep path, 4.3 → 3.8 s (within noise) because the loops waited on memory. Kept, but only worth it once states stay in cache.
- **`&dyn Fn` element callbacks to share the serial and parallel kernel loops** (2026-11-08): slower than the original (p = 1e-4 case 0.76 → 1.2 s). Use generic helpers.
- **A fresh `Vec` per dense measurement** (2026-11-08): above 128 KB glibc maps fresh pages, page faults every time. Reuse one buffer per batch.
- **Dead end: sampling all final measurements of a group from one transformed state** (2026-11-08, Next of 0.1.8). Considered in detail: a measurement tree costs ~k/2 shots' worth of dense work, and applying the whole Clifford at full size costs more passes than the sequential halving. With 1–2 shots per group at p = 1e-3 neither helps; the one-pass retirement does. Retry if groups stay large (low noise, many shots) and the final dense measurements dominate.
- **A copy of the Clifford frame per group** (2026-11-06). 2.8× slower at 200 qubits, though 14–40% faster at 60–100; summed on one thread 22.7 s against 15.2 s for the shared frame.
- **Pre-trajectory sampling for state-vector, MPS and near-Clifford** (2026-10-28, Patti et al. arXiv:2504.16297): simulate each distinct error pattern once for all shots that drew it. Fully implemented, and it passed exact-distribution tests on every backend, but it was **lost**: that run couldn't push (HTTP 403). It is not rejected; it was replaced by frames on near-Clifford (0.1.8), and the other backends reject noise. Retry if noise is wanted on the state vector or MPS.

**Dense kernels (`nearclifford/dense.rs`, `dense/avx2.rs`, 2026-11-10)**
- **Scalar rewrite alone**: blocked signs (table of the low bits, one population count per 16), unchecked indexing, four accumulators. Expectation 1.7×, retirement 1.6×, rotation 1.3×; the Z-type rotation got slower (0.85 → 1.5 ns) with per-element complex factors. Contiguous (lowest X bit ≥ 4) and XOR-scrambled partner loads ran equally fast: the loops were at scalar throughput, not memory- or gather-bound. Replaced by AVX2; only the multi-accumulator serial sum kept.
- **Blocking contiguous below the lowest X bit** (planned, not built): 6 of 14 measured and 4 of 14 rotation Paulis of the 100-qubit benchmark have X at position 0, where the blocks are one amplitude. The register-pair formulation (`i ^ xh`, swap for bit 0) covers every Pauli.
- **A population count per register for the signs** (first AVX2 version): retirement 0.64–0.66 ns per input amplitude; a block table brought it to 0.32–0.48.
- **Full-sum expectation with both `Re` and `Im` accumulators**: 0.42–0.47 ns per amplitude; pairs once with the one product the phase needs: 0.22–0.35.
- **Dead end: nested parallelism.** Forcing the dense kernels serial inside each batch (`PARALLEL` = 2^24) changed nothing (2.41 s against 2.28 s, noise).

**Python output (`python/src/lib.rs`)**
- **Unpacking bits with NumPy in Python** (2026-10-31): d = 21 took 0.69 s, slower than Stim, while sampling took 0.09 s.
- **Writing into a Python `bytearray`** (2026-11-02): it is zeroed by one thread in 4 KB pages, giving 1.04× the old time at d = 21. Use `numpy.empty`, which gets huge pages and no zeroing: 0.64–0.75×.
- **A thread pool per step, or two visits to one pool** (2026-11-02): showed in millisecond calls at d = 11.
- **A table of per-row slices for the transpose** (2026-11-02): 2 MB at d = 51, measurably slower than computing row offsets.
- **PyO3's buffer protocol** (2026-11-02): unavailable under `abi3-py310` (it needs the 3.11 limited API). Use `__array_interface__`.

**Pauli propagation (`pauliprop`)**
- **Clifford perturbation theory's angle split, θ − π/2 plus a Clifford** (2026-10-28, arXiv:2306.04797). With a coefficient threshold it keeps exactly the same strings. Retry only for truncation by perturbative order.
- **Known limits, measured, not fixed** (2026-10-28):
  - 20 steps near θ_h = π/2 grows to tens of millions of strings;
  - θ_h = 0.6 at 20 steps is not converged at 1e-5;
  - θ_h = 1.0 at 1e-5 runs out of 15 GB;
  - the dropped-one-norm bound is far above 1 at 20 steps.

**Benchmarks and checks**
- **Comparing `.text` across a version bump** (2026-11-12). Every example binary differed from 0.1.10's even where no code changed: the version enters the symbol hashes, which move the layout. Build the "before" sources with the version bumped too; then `bench`, `pauliprop`, `stabilizer` were byte-identical.
- **Treating 1.03–1.04 medians on `shots` and `mps` as regressions** (2026-11-12). Their hot functions had the same sizes in both builds (only noisy-path symbols differed). `shots`: 60 rounds read 1.033, the next 60 1.004; `mps qft 100`: 1.036 over 60, then 1.000 over the next 60. Rerun 60 rounds before believing a 3–4% reading.
- **Stim circuits with one target per line** (2026-10-29). Stim needed 268 MB at d = 21, and at d = 51 used 14 GB and was killed. Ungrouped circuits also flattered Qevedo's noiseless speed-up: 1.7× at d = 21. Always group instructions (as `compare_stim.py` does) and warm Stim up first.
- **Distance-101 bool detection events** (2026-10-31): about 10 GB, too big for the 15 GB VM. Use bit-packed output.
- **Comparing sets of distinct outcomes in random-circuit checks** (2026-11-04): fails when there are more outcomes than shots. Compare the affine span.
- **Treating |z| ≈ 2–3.5 in agreement checks as a bug** (2026-10-31, 2026-11-04). The deviations vanished at 1–24 M shots and changed sign between seeds. Rerun with more shots and seeds before suspecting anything.
- **An exact noisy test over 4ⁿ branches** (2026-10-29): it took 68 s. Restricted to 2 qubits it takes 4.9 s.
- **An apparent MPS QFT-100 regression** (2026-11-04): a 1.088 median over 25 pairs was noise (60 alternating pairs gave 0.986). Valgrind is unusable on binaries built for the native CPU.

## Method lessons

- **A row's cost is per column bit** (2026-11-22): callgrind's per-line counts showed the column-major row gather at ~13 instructions per bit, two of them a bounds check; slicing the table to the exact range before the loop removed it (−0.14e9). Check per-line counts of any strided loop.
- **`--only` matches substrings** (2026-11-22): `compare_examples.py --only "24 T"` also ran the 10k and 100k cases; name cases precisely or expect the extra rounds.
- **The noisy benchmarks need `clifft` in both venvs** (2026-11-22): `compare_noisy_builds.py` imports `bench_noisy_nearclifford`, which imports Clifft; `pip install clifft` into each venv first.
- **Count the words a batched pass reads before building it** (2026-11-20): a pass that classifies all n rows at once read three rows' worth of the column-major frame, while the per-row scan it replaced read 2.5 rows a call; an atomic counter of calls and classifications (two minutes) would have shown it before three versions were built.
- **Record peak RSS for any memory-reuse change** (2026-11-20), on one thread and four: the fastest buffer pool cut faults 45% and time up to 13%, and raised peak RSS 25% / 75%. `/usr/bin/time` is not on the VM; `resource.getrusage(RUSAGE_CHILDREN)` after `subprocess.run` gives `ru_minflt`, user and system time and `ru_maxrss`.
- **glibc's mmap threshold moves only on `free`** (2026-11-20): shrinking a mapped block with `realloc` keeps its pages but leaves the threshold at its initial 128 KB, so every later large allocation is a fresh mapping. Check faults, not just time, after changing who frees what.
- **Measure the noise floor with an A/A run** (2026-11-18): `compare_noisy_builds.py` with the same environment as before and after read 0.770-1.434 best-of in 5 rounds on runs of 6-50 ms; recheck such cases with `--qubits N --rounds 40` (they then read 0.971-1.017).
- **Callgrind works on x86-64-v3 builds** (2026-11-18): the "Valgrind is unusable" note is about `-C target-cpu=native` (AVX-512); `RUSTFLAGS="-C target-cpu=x86-64-v3" cargo build --release --example nearclifford --target-dir <scratch>` then `valgrind --tool=callgrind` on 20,000 shots ran in about a minute and gave per-line instruction counts (`callgrind_annotate --auto=yes`), which found the non-zero frame columns in `extract` that timers could not.
- **Counts digests in Rust** (2026-11-18): a temporary example (copied into both trees' `examples/`, not committed) hashing `RunResult.counts` with `DefaultHasher::new()` (fixed keys, so stable across processes) over 84 cases (7 circuits including mid-circuit measurements and resets; 1, 777, 10,000 shots; 1 and 4 threads; 2 seeds) checks a change that keeps the draws in a minute, without wheels.
- **Count calls, not only time** (2026-11-18): an atomic counter of `kind` calls and of measurement steps (307,502 against 107,614 after the change) showed the quadratic scan directly.
- **Run clippy after the last edit, tests included** (2026-11-16): clippy ran before the new unit test was written; CI's `needless_range_loop` then failed the feature commit and took a fix commit. Rerun `cargo clippy --release --all-targets -- -D warnings` right before committing.
- **Time per operation kind before choosing a speed-up** (2026-11-16): `Instant` timers per `Act` kind plus finer ones inside `MeasureDense` (expectation / decide-and-split / retire) and an event count took two builds and 10 minutes, and overturned the guess in Next (kernels) in favour of allocations (1.65 µs of bookkeeping per split event against 0.35 µs of kernels).
- **A layout change that keeps the draws is proved by digests first** (2026-11-16): `hashlib` digests of counts on 19 seeded cases (1, 777 and 10,000 shots, 1 and 4 threads, resets) were identical to 0.1.12 before any timing; a mutation (skipping the in-place compaction) failed the new unit test and five exact-distribution tests.
- **1-shot runs under a millisecond read ±20% in 5 rounds** (2026-11-16): the 24-qubit 4-thread case read 1.208 best-of in 5 rounds and 0.934 over 20; recheck such readings with `--qubits N --rounds 20` before believing them.
- **Mutation check for a new exact identity** (2026-11-14): deleting the one line that applies it (the row flip) and rerunning `tests/nearclifford.rs` showed which tests can see it (4 failed). Cheap proof that the tests cover the change.
- **`.text` of the examples settles most of the 3% rule** (2026-11-14): with both builds at the new version, six of ten example binaries were byte-identical; only `shots`, `mps`, `nearclifford` (and untimed `quickstart`) needed interleaved timing.

- **Build the "before" wheel from `git archive HEAD`** (2026-11-12): the first baseline build ran from the working tree while the change was being written and failed on half-edited code. Export HEAD to the scratch directory and build there; bump its version too if `.text` is to be compared (above).
- **Check counts digests first** (2026-11-12): a change that keeps the random draws should give identical counts for a seed; `hashlib` digests of `RunResult.counts` for five circuits in both venvs settled correctness in seconds, before any timing.
- **Few-shot runs show fixed costs** (2026-11-12): timings at 10,000 shots hide per-run compile work; `compare_noisy_builds.py --shots 1` showed the first version of the change 1.04–1.56× slower there while 10,000 shots were 0.25–0.93.
- **Count both sides of a meet-in-the-middle** (2026-11-12): propagating whichever side has fewer Paulis, in the picture where they are sparse, took a 30 ms pass off the run (one shot at 200 qubits 0.66 of 0.1.10's time instead of 1.46); temporary `Instant` timers around compile / link / run found where the time went.
- **Floating-point sums are latency-bound** (2026-11-10): a sum over 2^14 cached terms with one accumulator ran at 2.1 ns per term, with eight at 0.3. Check any `.sum()` in a hot loop.
- **Microbenchmarks on the VM** (2026-11-10): single timings of the same kernel moved ±50% between runs; best of 30 interleaved repetitions (old, new, old, ...) of 100 calls was stable to a few percent.
- **Benchmark the shipped instruction set** (2026-11-10): `.cargo/config.toml` builds for the native CPU (AVX-512 here); wheels are x86-64-v3. Set `RUSTFLAGS="-C target-cpu=x86-64-v3"` for both before/after wheels, and run the tests once with `-C target-cpu=x86-64` (a separate `--target-dir`) to cover the scalar fallback.
- **Benchmark rows name the version** (2026-11-10): `bench_noisy_nearclifford.py` reads it from the installed wheel, so bump the version locally before the timing runs (commit the bump separately as the release).
- **`.text` comparison settles example outliers** (2026-11-10): `objcopy -O binary --only-section=.text` on both builds; `bench`, `stabilizer`, `pauliprop` were identical, so their 1.02–1.06 medians needed no rerun.
- **Release workflow flakes** (2026-11-08): 0.1.9's Release run failed only because the macOS arm64 job got HTTP 504 installing maturin; nothing was published. Check which job failed before suspecting the code; a rerun of the failed jobs is the owner's call.
- **Profiling without perf** (2026-11-08): no `perf` on the VM. Temporary `Instant` timers per operation kind in the hot loop (and a count of amplitudes touched) found the bottleneck within minutes; per-amplitude ns from those counts told memory-bound from compute-bound. Remove them before committing.
- **Python environments** (2026-11-08): `/usr/local/bin/pip` belongs to Python 3.13 while `python3` is 3.11, and Clifft needs ≥ 3.12. Make one `python3.13 -m venv` per build (before / after) and install each wheel there; `compare_noisy_builds.py` takes the two interpreters.
- **Comparing counts across builds:** Python's `hash()` of a string is salted per process; use `hashlib`.

- **Timing on the VM.**
  - Builds drift ±8–10% between batches and 3-repeat runs move ±15%.
  - Compare before and after with paired, randomly ordered runs (15–60 pairs).
  - Millisecond calls need hundreds of repetitions.
  - Compare `.text` of unchanged benchmark binaries: identical code can't have regressed.
- **CI.**
  - While master's version equals PyPI's, `pip install --find-links dist` in `ci.yml` installs the published wheel, so feature commits fail on macOS and Windows until the version bump. This is known and harmless; don't chase it.
  - CI uses the latest stable clippy, which can be newer than the run's: 1.99 rejected code that 1.97 passed and stopped 0.1.7. Update the toolchain before releasing.
